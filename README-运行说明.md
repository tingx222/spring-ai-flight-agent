# Spring AI Alibaba 机票售后助手

完整技术栈、IDEA打开步骤、架构/时序/状态/RAG图及面试讲解见 [项目讲解与源码阅读指南](项目讲解与源码阅读指南.md)。以下使用说明含迭代记录，当前执行行为以“操作预览与确认”一节及完整指南为准。

基于官方 `playground-flight-booking` 示例整理，保留原项目许可证和代码。适合先运行、读懂，再扩展为求职项目。

## 启动

1. 双击本目录的 `start.cmd`。
2. 按提示输入自己的阿里云百炼 API Key（中国内地服务，输入不回显）。密钥仅传入本次启动进程，不写入源码或配置文件。若已配置 `AI_DASHSCOPE_API_KEY` 环境变量，则不会再次询问。
3. 等待终端出现 `Started AgentApplication`，浏览器打开 http://localhost:9000 。启动时会调用 embedding 接口建立条款索引，需要网络和有效密钥。
4. 按 Ctrl+C 停止服务。

需要 Java 17+。首次无 jar 时会自动构建，构建需要 Maven 3.9+ 和网络。项目包含已构建的前端，无需单独安装 Node 依赖。

API Key 获取入口：https://bailian.console.aliyun.com/ 。需要有聊天模型 `qwen-max` 和文本向量模型的调用权限及可用额度；模型调用可能产生费用。不要把密钥提交到 Git。

端口被占用时，在 PowerShell 中运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start.ps1 -Port 9001
```

## 可以怎样体验

页面展示 5 条模拟订单，可结合订单列表对话：

- “我是云小宝，请查询预订号 101 的订单详情。”
- “有哪些退票和改签规定？”
- “我是李千问，取消预订号 102 的订单。”
- “我是张百炼，把预订号 103 改签到 YYYY-MM-DD。”（替换成实际未来日期）

## 当前边界

这是机票售后教学示例：查询已有订单、改签、取消、条款 RAG、流式对话和会话记忆。没有真实车票/机票库存、新购票、支付、登录鉴权或生产级订单保护。订单、对话和向量存在内存中，重启后重置。姓名与订单号查询仅为演示，不能当作真实身份认证。

## MySQL 持久化模式

默认 start.cmd 仍使用内存订单。新增加 start-mysql.cmd，启用 mysql profile；切换存储模式前先停止旧服务，避免9000端口冲突。

1. 启动本机 MySQL，在自己的客户端登录。执行同目录 mysql-init.sql 创建 flight_booking 独立数据库（不修改已有业务库）。
2. 运行 build.ps1，打包最新代码。
3. 双击 start-mysql.cmd。默认 localhost:3306、root、flight_booking；输入数据库密码和百炼密钥，均隐藏输入，不写入文件。
4. 需要修改连接信息时，在 PowerShell 当前窗口设置 DB_HOST、DB_PORT、DB_USERNAME、DB_NAME，再运行 .\start-mysql.ps1；不要将密码写进脚本或提交到 Git。
5. 首次空表初始化5条演示订单，以后不覆盖、不重置。内存模式中已做的改签、取消不会自动迁移。
6. 改签103并取消102后停止服务，再以 MySQL 模式启动。刷新 /api/bookings 核对日期和取消状态保留，这是实际持久化验收。

调用链：CustomerSupportAssistant → BookingTools → FlightBookingService → BookingRepository。MemoryBookingRepository 保留演示存储，JdbcBookingRepository 使用 JdbcTemplate 参数化SQL。原有业务规则及工具、接口保持不变；DemoBookings 提取官方随机数据生成逻辑。

仅订单持久化；聊天记忆和条款向量仍在内存。首次初始化面向单实例本机演示，尚未实现生产迁移管理、完整的跨实例订单协调、鉴权、退款。root仅沿用本机开发连接，部署应使用专用最小权限账号。当前连接选项面向本机开发。


## 订单业务规则（Java 层）
- 已取消订单拒绝改签。
- 改签目标日期不能早于当天；空日期、格式错误或不存在的日期会被拒绝。
- 重复取消返回“订单已取消，无需重复操作”，不再写数据库。
- 保留原示例对原航班日期的改签、取消限制（LocalDate 按天判断，非精确小时）。
- 工具将业务校验失败作为明确结果交给模型，避免空成功结果。数据库等系统异常仍向上抛出。

手动验收：对已取消的102再次取消，再尝试改签，应提示无需重复取消、不能改签；对确认状态的103尝试改到过去日期，应拒绝且数据库不变。随后选择未来日期改签，检查正常路径仍可用。
规则在业务层生效；后续增加了事务内订单行锁和单实例确认保护，但数据库幂等请求号、跨实例协调及已完成订单状态管理仍待完善。


## 预订号输入校验
用户消息中明确写“预订号102”“订单号：102”，或单独回复“102”。只从当前会话中的用户消息提取预订号，不信任模型回复或检索文档中的编号。编号通过ToolContext传给工具；模型传入的编号不在该集合中时，三个订单工具都不会调用业务层。缺号且识别为订单操作时直接追问，并将追问记入会话记忆。
查询失败返回success=false及明确说明，不再返回看似存在的空订单。条款问答仍走原RAG。此校验不是鉴权，也不能完全消除模型文本幻觉；会话记忆被清空或编号移出记忆窗口后需要重新提供。
验收请新建会话：只提供姓名日期航线取消→应只追问编号；再回复“预订号102”→可继续；新会话用“预订号999，姓名李千问”查询→应明确未找到；条款问答不应被编号追问拦截。


## 操作审计
MySQL模式启动时自动创建booking_audit表，不覆盖已有订单。通过业务服务执行的改签、取消记录时间、订单号、动作、结果、说明与修改前后快照。结果：SUCCESS成功，REJECTED业务规则拒绝，NOOP已取消而未重复修改。快照仅保存日期、状态、航线、舱位，不保存密钥、完整对话或认证身份。
MySQL模式中，订单更新与审计插入处于同一事务；审计写入失败则订单回滚。业务拒绝也提交审计，再向工具返回拒绝结果。操作期间对匹配订单加行锁。内存模式记录也可查询，但重启重置。
浏览器查看：http://localhost:9000/api/booking-audits 或 http://localhost:9000/api/booking-audits?bookingNumber=102 ，最多返回最新100条。Navicat可刷新查看booking_audit表。
缺少预订号时被输入校验拦截的请求、查询操作、未到达Java业务服务的模型拒绝、数据库故障本身不写本表；不应声称审计覆盖所有聊天和系统失败。审计接口和订单接口一样尚无鉴权，仅用于本机演示。数据库初始化订单不记业务审计。
验收：对已取消102再次取消，查看NOOP；尝试对103改到过去日期，若模型实际调用工具则查看REJECTED且前后快照一致；对确认状态订单正常改签到未来日期，查看SUCCESS及日期变化。重启MySQL模式，历史记录仍保留。


## 对话体验修复
支持“预订单101”“预定号101”和“101，云小宝，改签”等编号表达；排除常见日期、金额、航班代码中的数字。只保留用户最近一次明确提供的一组编号作为当前订单上下文，模型回复中的编号不参与授权。仍不是身份认证。
会话历史改为按角色传递，显式设置最近100条消息；页面刷新会生成新chatId，服务重启也会清空聊天历史，订单及MySQL审计不受影响。
日期支持10.20、10月20日、10/20、明天、后天及完整年月日。缺少年份按当年理解，不自动推至下一年；过去日期与非法日期仍由业务层拒绝。
工具和提示词明确没有实际扣费或退款。前端请求编码消息参数，发送即加锁，忽略空消息；已同步已编译资源并更新引用，避免浏览器复用旧JS。
回归验收：新会话依次发送“我是云小宝，预订单101”“改签到10.20”，应沿用姓名编号、接受简写日期；模型如果询问具体操作与费用，再回复确认。检查订单接口和审计，不能只看助手文字。是否自然理解仍需真实模型验收。
当前边界：后续已增加后端预览确认，详见末尾“操作预览与确认”。聊天与待确认方案仍未持久化，跨年日期需用户明确；输入提取并非通用语言理解器。


## 日期改签航线保护与旧数据修复
仅改日期时，空/null/空白航线参数沿用数据库原航线；明确要求不同航线会拒绝。MySQL日期改签SQL本身只更新日期，内存模式也不再更新航线。
针对旧版本可能清空的航线：MySQL模式启动时，仅对航线缺失的订单，从最近100条审计中寻找完整、且与现有非空航线部分一致的快照；只恢复航线，不回退日期或状态。修复和REPAIR审计同事务提交，再次启动不会重复修复。没有匹配快照则记录警告并拒绝该订单继续改签，不凭模型回复或默认城市填值。
姓名提示新增识别“云小宝，101”等用户原话，帮助模型避免重复问姓名；它仍不是登录或身份认证。
验收：启动后检查101的日期仍是已改签日期，航线应从历史审计恢复为深圳→上海，并查看REPAIR记录。再只说改日期，确认接口和审计中的航线保持不变。


## 操作预览与确认
对话中的改签、取消工具现在只生成方案，订单保持不变；后端显示订单号、姓名、前后日期、航线及条款金额。方案5分钟有效。下一轮单独回复“确认”“是”等，后端执行该会话已展示的具体方案，不提供模型可调用的确认工具。
新日期、新订单或新操作会撤销旧方案再重新预览；“算了”“撤销”等撤销方案。确认时在事务中比较订单快照，订单变化则拒绝，执行时仍重新校验业务规则。成功、拒绝或系统异常后旧方案不再执行；重复确认只返回已处理结果。
待确认方案及已处理结果暂存在单实例内存，重启/换会话后需重新预览。确认状态不是数据库持久化的请求幂等表，不应声称支持跨实例或跨重启的幂等；用户身份仍未认证。业务服务保留内部直接操作方法用于测试和受控调用，模型仅能访问预览工具。未确认预览不写执行审计。
验收：提出改签→检查订单未变→回复确认→订单变化并出现一条执行审计→再次确认无新增执行。再生成方案并改日期，应生成新方案；其他会话、过期方案或已变化订单都不能用旧方案执行。

确认策略补充：在预览后发送任何非确认消息，旧方案失效；若还需要执行，请重新生成预览。这样可避免离题后一句“好的”误执行先前操作。该策略偏保守，费用问答也会使旧方案失效。
